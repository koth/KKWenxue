## Context

目前在线导入链路是“目录元数据 → relay 创建正文抓取任务 → worker 下载整本 TXT → worker 打 ZIP → App 导入成一个新的 `Book.id`”。`BookDatabase` 只保存书籍和章节正文，没有远程绑定、revision、章节哈希或历史版本；`BookImporter.parseCatalogText` 又用整包内容哈希生成本地 ID。因此网站新增章节后，重新导入会产生第二本书，原阅读进度无法可靠迁移。

目标是把在线书籍从一次性文件导入升级为可更新的本地内容实体，同时保留本地 TXT/EPUB 的离线导入语义。网站是变化源，服务端负责抓取和中转，App 只处理已验证的内容包；阅读器和听书系统继续以稳定的章节 ID 与 UTF-16 文本锚点工作。

## Goals / Non-Goals

**Goals:**

- 为在线书籍建立稳定的远程身份、本地 active revision 和章节内容哈希。
- 以轻量版本检查替代每次整本下载，支持新增章节优先的增量更新。
- 通过服务端/relay 中转正文，App 不接触书源和 worker 局域网地址。
- 原子合并、失败不覆盖、可回滚，并恢复阅读进度、书签、评论和音频关联。
- 支持启动/前台检查、纯新增章节自动更新、任务恢复和幂等重试。

**Non-Goals:**

- 首版不实现任意两本本地书的自动合并或全文三方合并。
- 不把网页正文直接暴露给 App，也不在 App 内实现书源解析器。
- 不自动更新后立即合成新章节 TTS；只标记旧音频与正文 revision 的关系，后续由听书/TTS 流程处理。
- 不自动更新本地 TXT/EPUB；在线书籍默认自动下载纯新增章节，用户可暂停自动更新或限制网络类型。
- 不自动应用包含改章、删章或重排的高风险变更；这类更新需要用户确认，避免静默破坏用户正文和锚点。
- 不承诺远程删除章节后恢复原章节内容；历史 revision 仅在本地保留的回滚窗口内可用。

## Decisions

### 1. 稳定身份与版本模型

- 在线书籍本地 ID 使用 `online:<source>:<remoteBookId>`，与内容哈希无关；远程绑定单独保存 `source`、`remote_book_id`、`remote_latest_chapter_id`、`active_revision` 和同步时间。
- 章节 ID 优先使用网站稳定 chapter ID；如果书源只能提供顺序和标题，服务端生成内容寻址 ID，并把“顺序变化/标题变化”列为需要确认的变更。
- 每个正文 revision 保存 immutable manifest 和章节内容快照。`active_revision` 指向当前阅读版本，历史版本只保存 manifest、哈希和回滚所需正文文件。
- 旧的 `local-<hash>` 在线导入书籍不能凭标题自动转换；新增“关联在线书籍”时要求用户从搜索结果中确认，完成一次受控迁移。

备选方案：继续以整本内容哈希作为 `Book.id`，每次更新复制书籍并迁移进度。该方案会破坏书架引用、音频和评论关系，故不采用。

### 2. 版本检查与更新计划

- 目录 API 增加 `GET /v1/catalog/books/{id}/version`，只返回最新章节 ID、章节数、更新时间、远程 revision/manifest 摘要和检查时间。
- 增加 `POST /v1/catalog/books/{id}/update-plan`，body 包含本地 active revision、已知章节 ID/哈希摘要和目标 remote version。服务端返回新增、修改、删除章节以及预估大小。
- App 进程启动和恢复到前台时由同步协调器触发检查；同一轮生命周期内对同一本书去重并短时防抖，用户手动刷新可立即检查。版本检查失败不影响离线阅读。
- plan 使用 `bookId + fromRevision + toRevision` 幂等键并设置过期时间。下载前再次确认 `fromRevision`，防止旧计划覆盖新版本。

备选方案：每次请求完整目录或完整 TXT 后在手机比较。该方案浪费带宽、暴露正文接口且无法安全支持大书，故不采用。

### 3. 服务端内容和包协议

- worker 继续抓 TXT，但在服务端先形成内容寻址章节快照；以目录服务提供的远程 chapter ID/顺序元数据建立 manifest。
- 新包包含 `schema_version`、source/book ID、`from_revision`、`to_revision`、章节列表、每章 `chapter_id/title/body_sha256/body`、删除列表、字数统计和整体 SHA-256。
- append-only 更新包只带新增章节；存在改章/删章时返回完整变更列表，必要时打包含受影响章节的新正文。
- 目录 API 和 relay 只暴露任务状态及下载 URL；App 对 HTTP 202、过期、失败和中转错误分别处理。worker 失败不得让旧任务看起来像可下载 ZIP。
- 服务端以 `content.update:<bookId>:<from>:<to>` 去重，抓取、打包和中转均可重试；内容包生成采用临时文件 + 原子 rename。

### 4. Android 本地存储与原子应用

- `BookDatabase` 升级到新 schema：保留现有 `books/chapters` 兼容读取，新增 `online_bindings`、`book_revisions`、`revision_chapters`、`sync_jobs`；必要时逐步把正文存储从单一 active 表迁移到 revision 关联表。
- 更新流程为：下载临时包 → 限制大小并校验 manifest/整体哈希 → 在 SQLite transaction 中校验 `from_revision`、章节 ID/顺序/正文哈希 → 写入新 revision 和章节 → 更新 active revision → 提交 → 清理旧临时文件。
- 更新前创建上一版本的保留标记；至少保留当前版本和最近一个可回滚版本。空间不足时先报告，不删除 active revision。
- App 重启后依据 `sync_jobs` 恢复状态。已提交的 `to_revision` 任务视为幂等完成，未提交任务清理临时文件并可重试。

备选方案：直接覆盖现有 `chapters` 表。该方案无法回滚，且更新中断会造成半本书，故不采用。

### 5. 阅读/听书锚点迁移

- append-only 时旧 chapter ID、旧 `Chapter.text` 和 UTF-16 offset 完全不变；`ReaderStore` 只需更新总章节/总字数来源。
- 改章时服务端提供旧/新摘要，客户端以旧 offset 附近的短上下文和稳定边界尝试唯一匹配；成功记录迁移方法，失败保留旧锚点并提示用户重新定位。
- 书签和评论记录 `revision`、chapter ID、start/end、quote；不能匹配时显示“原文已更新”，不删除用户内容。
- 音频 manifest 的 `source_revision` 必须与当前 active revision 匹配才显示为当前可听；旧 artifact 保留在音频库但不自动绑定到新正文。

### 6. 更新策略与用户体验

- App 启动/恢复前台时启动同步协调器：先批量轻量检查书架上的在线绑定，再按并发上限创建更新计划。检查不阻塞首页、书架或离线阅读。
- 默认模式：检查自动、纯新增章节自动下载并合并；更新卡片显示“正在更新/新增 N 章/已是最新/更新失败”等状态。包含改章、删章或重排的计划只进入待确认状态。
- 自动更新任务使用 2～4 本书的客户端并发上限，并按用户网络策略决定是否下载；同一本书始终只有一个活动任务。
- 同步页面显示检查、生成计划、抓取、等待中转、下载、校验、合并、完成/失败阶段；错误显示阶段化文案，不直接展示 worker 堆栈。
- 自动更新完成后展示摘要，但不得自动切换当前阅读章节、改变阅读页、启动播放或重建当前音频队列。用户取消只取消本地等待/下载，不撤销已经开始的服务器抓取任务。

## Risks / Trade-offs

- [书源章节 ID 不稳定] → 服务端建立 ID 质量检查；无法确认时降级为内容寻址并要求用户确认，不自动重排旧章节。
- [大书更新包占用空间] → append-only 优先、包大小/磁盘余量预检、临时文件与历史版本采用配额。
- [旧导入书无法判断远程来源] → 不自动猜测；提供显式绑定流程，并保留原书备份直到迁移完成。
- [章节改写导致音频失配] → source revision 强校验；旧音频只作为历史 artifact，不冒充当前正文。
- [服务端任务长时间失败] → 使用幂等 plan、任务 TTL、指数退避和可重试错误分类；客户端始终保留旧版本。
- [更新时 App 崩溃] → 数据库事务只在完整校验后切换 active revision，启动时清理未提交 staging 目录。

## Migration Plan

1. 先升级目录服务和正文 worker，新增版本检查/更新计划/增量包协议，旧的整本导入接口继续可用。
2. 升级 App 数据库，给新在线导入书籍建立 binding；旧本地书籍保持原 schema 读取。
3. 对历史在线书提供显式“关联在线书籍”入口，验证标题、作者和用户确认后生成稳定在线 ID；迁移失败不删除旧书。
4. 灰度启用“检查更新”，先对纯新增章节自动下载并应用，同时对改章/删章/重排只展示待确认计划；验证真实书籍的新增章节、失败恢复和多书并发限制。
5. 保留旧整本下载作为兼容和灾备路径，并逐步开放自动更新暂停、网络限制和回滚入口。
6. 回滚时停止新更新 API 的客户端入口，继续提供旧包下载；已完成的本地 revision 不回退，除非用户主动选择回滚。

## Open Questions

- 书源是否能为每章提供长期稳定的 chapter ID；若不能，内容寻址 ID 的改章判定阈值需要用真实书籍校准。
- 首版历史 revision 保留数量和磁盘配额按“最近 1 个版本”还是按固定 GB 限制。
- 是否在后续版本提供用户开启的 Wi-Fi 自动下载，而不是只做每日检查。
- 章节删除/重排时，阅读器是否需要展示“原章节已下线”的历史阅读入口。
